# Database agent handoff

Created migrations `20261014000100_bank_schema.sql` and `20261014000200_bank_rpcs.sql`, integration tests `supabase/tests/bank.integration.mjs` and `bank.concurrent.mjs`, read-only `supabase/inspect/preflight.sql`, and `docs/DATABASE.md`. The actual project was inspected through Supabase's read-only Management API before migration on 2026-10-14. `public` contained the expected legacy `profiles`, `offers`, `wants`, `exchanges`, and `transactions` tables; exact row counts were 1, 1, 1, 0, and 0. There were 4 `auth.users` rows. The sole legacy `profiles.time_balance` was zero, with no negative or fractional-minute values. No migration history relation existed before application. A private preflight is saved at `.private/preflight-readonly-20261014.json` (mode 0600). The Management API returned no backup entries; WAL-G is enabled and PITR disabled. This is not evidence of a downloadable disaster-recovery backup.

A scoped legacy rollback snapshot is saved privately as `.private/legacy-snapshot-20261014.json` and `.private/legacy-restore-20261014.sql` (both mode 0600). It includes all five public table rows, column definitions, constraints, indexes, RLS policies, function and trigger definitions, table/sequence/function grants, sequence state, and `auth.users` ID/confirmation stubs. Restore was tested on PGlite and a disposable real PostgreSQL 18.4 database. The real restore matched source rows, captured object definitions/grants, and sequence state; `pg_dump` then produced `.private/legacy-clone-20261014.dump`, which was restored into a second disposable database. Applying both migrations to the actual live-shaped clone succeeded, retaining the original profile, offer, want, and zero balance while provisioning four accounts. The disposable databases and server were stopped. This is a scoped migration rollback/clone backup, not a full Supabase Auth or Storage backup. A direct production `pg_dump` still requires database credentials or configured JIT access.

The root agent applied the reviewed atomic transaction to the live project with `.private/apply-bank-migrations.mjs --execute` on 2026-10-14; the Management API returned HTTP 201. The transaction used SERIALIZABLE isolation, advisory and table locks, verified the exact five-table/Auth snapshot, applied both migrations, and recorded versions `20261014000100` and `20261014000200` in Supabase's standard migration table. The generated request SHA256 was `331077db69ae5ddc23906b2f194c8ad7198255fdbdb5e639740241a3aded2fe9`. Both migrations and the private snapshot were hash-pinned in the runner. Before application, two disposable PostgreSQL clones proved that a changed legacy row aborted without schema/history changes and an unchanged clone committed both migrations and history. A harmless live read-only probe confirmed that the Management API accepts a `BEGIN`/`COMMIT` batch.

The live 14-query read-only postflight **passed** and raw results are saved at `.private/bank-postflight-20261014.json` (mode 0600). Exact history versions, original profile/offer/want/Auth references, account opening entries, ledger totals, table RLS, client write revocations, profile column grants, all 22 bank function grants and SECURITY DEFINER settings, and legacy RPC revocations were verified. There are 4 accounts and 4 opening ledger entries, total balance 0, no negative accounts or ledger mismatches. The first verifier run reported a false failure because the hosted PostgreSQL serialized the explicitly empty function path as `search_path=""` while local PostgreSQL used `search_path=`. A separate catalog read confirmed all 22 live function definitions contain `SET search_path TO ''`; the verifier now accepts only those two exact empty-path encodings, and the rerun passed. No corrective production write was needed.

Contract changes communicated to root: add `bank_set_urgent_opt_in(p_enabled boolean)`, `bank_donate(p_minutes,p_note,p_request_id uuid)`, and `bank_contribute_project(p_project_id,p_minutes,p_note,p_request_id uuid)` with stable request UUIDs. Read RPCs `bank_project_summaries()` and `bank_account_summary()` return exact project and owner-only wallet totals; root loader should consume them. `exchanges.initiator_id` identifies the member who sent a request; the other member accepts. Legacy documented `time_credits` exchange tables are renamed to `legacy_exchanges`, retained with old transactions, and client access revoked. Historical exchange migration needs a separate reviewed reconciliation decision because the old design has mutable credits and may already contain transfers.

Security review focus: execute grants on every `bank_*` function, profile column grants, legacy function revocation, and concurrency behavior of simultaneous exchange confirmations and fund decisions. `node supabase/tests/bank.integration.mjs` passed locally after PGlite installation. It executes the read-only preflight both before and after migration, then checks legacy table preservation, orphan auth-user backfill, exact opening and welcome entries, profile/account grants and RLS (including a seeded old column grant), confirmation checks, participant privacy, both offer and want exchanges, reservation-aware donation, cancellation release, completion settlement, idempotent donation/contribution, facilitator-only approval and no self-approval, urgent opt-in, exact project summaries, direct-RPC validation, and public summary counts. `bank.concurrent.mjs` passed on a disposable local PostgreSQL 18.4 cluster: simultaneous 90-minute acceptances against 120 minutes allowed one reservation, donation could not spend reserved funds, cancellation released the hold, later acceptance and settlement succeeded, and simultaneous confirmation produced one ledger pair. The cluster was started on localhost:55437 and stopped after the test. Its pinned binary package `@embedded-postgres/darwin-arm64@18.4.0-beta.17` was installed only under `/private/tmp/bank-postgres-runtime`; the root package was not changed.
